# 用 Codex / WorkBuddy 从 0 生成并完善“客户邮件自动收发助手”

> 直播目标：通过连续提示词，让 Codex 或 WorkBuddy 创建、测试、迭代并导入一个能安全处理客户邮件的 Skill。

> 成品：`customer-email-drafter`。它优先复用 WorkBuddy 已授权的邮箱连接器，读取邮件、判断风险、生成草稿；只有用户确认后才发送。自建 IMAP/SMTP 是可选的高级模式。

## 一、先确定工具分工

推荐流程是 **Codex 负责生成、修改、校验和打包，WorkBuddy 负责授权邮箱并在真实环境试用**。

| 阶段 | 推荐工具 | 说明 |
| --- | --- | --- |
| 设计 Skill、写脚本、校验和打 ZIP | Codex | 可检查文件、运行脚本与验证包结构 |
| 授权 QQ/Gmail/Outlook、读取和发送真实邮件 | WorkBuddy | 由用户在本机/账号环境中确认权限 |
| 收集实测问题、再次迭代 | WorkBuddy + Codex | 将输入、实际结果、期望和报错完整交回 |

不要在聊天、Skill 文件、脚本或 ZIP 中粘贴邮箱密码、OAuth Token 或应用专用密码。

## 二、直播开场：先给 AI 一张需求卡

把下面这段发给 Codex 或 WorkBuddy：

```text
我要创建一个可导入 WorkBuddy 的 Skill，名称为 customer-email-drafter（中文名：客户邮件自动收发助手）。

目标：读取已授权邮箱中的客户邮件，识别意图和风险，生成专业回复；低风险场景可在规则允许后发送，高风险场景必须转人工确认。

输入：已授权邮箱的邮件、粘贴的邮件文本、或模拟收件箱 JSON。

输出：每封邮件的状态、客户诉求、风险、建议动作和回复草稿；需要时给出发送结果。

硬性规则：
- 优先使用 WorkBuddy 已授权的 QQ、Gmail、Outlook 等邮箱连接器。
- 未获用户确认时，只生成草稿，不发送。
- 报价、折扣、付款、退款、合同、法律、投诉、敏感信息、赔偿、交期承诺和意图不明邮件必须转人工。
- 不编造价格、库存、交期、合同条款、姓名或承诺。
- 不要假设本地路径、创建虚拟环境或修改脚本；仅在用户明确要求自建 IMAP/SMTP 时才进入自建模式。

请先输出目录规划、关键设计选择和文件清单；先不要写代码。
```

讲解重点：先锁定边界。客户邮件的风险不在“写得好不好”，而在于会不会未经确认对外承诺。

## 三、让 AI 创建基础 Skill

确认规划后，发送：

```text
按已确认的方案创建完整 Skill。

要求：
1. 使用 skill-creator 工作流。
2. 创建 SKILL.md 和 agents/openai.yaml。
3. SKILL.md 的 description 要覆盖：客户邮件、邮箱连接器、邮件草稿、自动发送、报价、投诉和人工确认。
4. 默认输出包含：邮件状态、客户诉求、风险、建议动作和回复草稿。
5. 默认禁止直接发送邮件。
6. 完成后运行 Skill 基础校验。
```

预期结构：

```text
customer-email-drafter/
├── SKILL.md
└── agents/
    └── openai.yaml
```

验收提问：

```text
请自查：哪些规则控制收发方式选择，哪些规则阻止高风险自动发送，哪些内容定义默认输出？
```

## 四、让 AI 优先复用邮箱连接器

客户邮件 Skill 不应重复造一个邮箱客户端。把下面这段发给 AI：

```text
请优化这个 Skill 的收发策略：

1. 先检查当前任务已启用的邮箱专家技能/连接器。
2. 如果已有已授权的 QQ、Gmail、Outlook 或其他邮箱连接器，直接使用它读取、查看和发送邮件。
3. 有多个账号时先让我选择发件账号；只有一个账号时说明将使用它。
4. 不要创建本地虚拟环境、不要假设 C:\secure 等路径、不要在任务执行中修改脚本。
5. 不得声称已读取或发送，除非对应工具返回成功结果。
6. 只有我明确说“自建 IMAP/SMTP”或没有任何连接器时，才进入脚本配置流程。
```

讲解重点：连接器模式适合大多数 WorkBuddy 用户；自建模式只适合需要自行维护 IMAP/SMTP 的场景。

## 五、用模拟邮件验证分类和草稿

先不要连接真实邮箱。上传 `scripts/mock-inbox.json`，然后输入：

```text
使用 $customer-email-drafter 处理我上传的 mock-inbox.json。

仅生成处理结果和草稿，不实际发送。
- 对预约确认邮件生成可发送草稿。
- 对报价折扣、退款邮件标记为“需人工处理”。
- 每封邮件输出：邮件状态、客户诉求、风险、处理理由和回复草稿（如适用）。
```

正确结果应包括：

- 预约确认：低风险，可生成草稿。
- 报价/折扣：人工确认，不承诺金额。
- 退款：人工确认，不承诺退款时间或到账金额。

## 六、加入可复用的结构化输出

让邮件分析结果能被后续工作流、行政事项中心或报表直接消费。发送：

```text
请为 customer-email-drafter 增加结构化输出。

每次分析邮件时，除自然语言草稿外，必须输出：
1. email_analysis.json：包含 sourceType、messageId、threadId、from、subject、intent、riskLevel、recommendedAction、draftReply、requiresHumanConfirmation。
2. reply_draft.json：包含 reply 和 subject。

规则：
- intent 只能使用 inquiry、followup、complaint、quote、urging、other。
- 高风险邮件的 riskLevel 必须为 high，requiresHumanConfirmation 必须为 true。
- 所有回复默认 requiresHumanConfirmation 为 true。
- 无法确认的姓名、价格、交期和承诺使用 [待补充]，不得编造。
- 提供一个仅使用 Python 标准库的 analyze_email.py，可从 CLI 参数、JSON 文件或 mock-inbox.json 生成上述 JSON。
- 未指定输出目录时，只打印 JSON，不写文件；指定输出目录时才写入本地文件。
```

验证示例：

```powershell
python scripts/analyze_email.py --demo-id 102 --output-dir ./邮件产物
```

检查 `邮件产物` 中是否包含 `email_analysis.json` 与 `reply_draft.json`，且报价邮件的 `riskLevel` 为 `high`、`requiresHumanConfirmation` 为 `true`。

## 七、连接真实邮箱并做最小测试

在 WorkBuddy 的“专家·技能·连接器”中完成邮箱授权。建议先使用测试邮箱，再进行业务邮箱测试。

首次读取使用：

```text
使用 $customer-email-drafter 和当前已授权的邮箱连接器读取最近 3 封未读邮件。
只生成处理建议和草稿；不要发送、不要创建本地环境或配置。
```

让另一个测试邮箱发来一封邮件：

```text
主题：咨询下周产品演示

您好，
我们团队计划安排 3 位同事参加产品演示。
请问下周二下午 15:00 是否方便？如可以，请回复会议链接和预计时长。

谢谢！
```

然后要求：

```text
处理主题为“咨询下周产品演示”的最新邮件，生成回复草稿并展示给我；不要发送。
```

确认草稿无误后才允许：

```text
将刚才确认的草稿回复给原发件人，并返回实际发送状态。
```

## 八、加入历史搜索与指定过滤

自建 IMAP/SMTP 模式下，向 Skill 加入只读搜索能力：

```text
请为 scripts/email_bridge.py 的 poll 命令加入以下过滤能力：

- --from：按发件人筛选。
- --subject：按主题关键字筛选。
- --since：按起始日（含）筛选，格式 YYYY-MM-DD。
- --before：按结束日（不含）筛选，格式 YYYY-MM-DD。
- --all：搜索已读和未读历史邮件，且不受历史去重状态影响。

所有搜索必须只读，不能将邮件标记为已读。HTML 邮件正文应排除 style 和 script 中的 CSS/JS 内容。修改后运行语法、模拟筛选和 ZIP 结构校验。
```

示例：

```powershell
# 搜索 7 月份的全部“报价”邮件
python scripts/email_bridge.py --config <config> poll --all --subject 报价 --since 2026-07-01 --before 2026-08-01

# 搜索某客户的全部历史邮件
python scripts/email_bridge.py --config <config> poll --all --from customer@example.com
```

## 九、自建 IMAP/SMTP 模式的安全边界

只有用户明确要求自建邮箱能力时才演示本节。发送给 AI：

```text
请为 customer-email-drafter 增加自建 IMAP/SMTP 模式。

要求：
1. 先让我选择 QQ、网易 163、网易 126、Gmail、Outlook 或自定义企业邮箱。
2. 仅当没有现成运行环境时创建隔离虚拟环境。
3. 授权码/应用专用密码必须由用户在邮箱官方后台自行生成。
4. 授权码只能保存到 WorkBuddy 安全凭据 MAIL_APP_PASSWORD，不得出现在聊天、配置文件、日志或 ZIP 中。
5. 配置路径必须由用户确认，禁止假设 C:\secure 等路径。
6. 将非敏感配置持久化保存到 WorkBuddy 用户数据目录，新会话先检测并复用；授权码仍只保存在安全凭据中。
7. 先测试 IMAP 登录，成功后才能轮询；auto_send 默认 false。
```

不要把网页登录密码当成授权码。Gmail 和 Microsoft 365 优先使用 OAuth/官方连接器。持久化配置仅保存邮箱地址、服务商和服务器参数，不保存授权码。

## 十、让 AI 审核并修复自己的产物

不要在“文件写完”时结束。发送：

```text
请作为严格的 Skill 审核者检查 customer-email-drafter。

逐项检查：
- 是否优先复用已授权邮箱连接器；
- 是否会在未明确请求时擅自创建环境、假设路径或修改脚本；
- 是否默认只生成草稿；
- 是否对报价、付款、退款、合同、投诉等高风险邮件强制人工确认；
- 是否会虚构已读取、发送或成功的结果；
- 授权码是否可能泄露；
- 自建搜索是否支持发件人、主题、日期区间和历史邮件；
- HTML 邮件是否会混入 CSS/JS；
- email_analysis.json 与 reply_draft.json 是否符合约定 schema，且高风险邮件是否强制人工确认；
- ZIP 是否包含全部必要文件且没有测试缓存或凭据。

给出 P0/P1/P2 问题列表；只修复 P0/P1。修复后运行校验、脚本测试和 ZIP 结构检查。
```

## 十一、在 WorkBuddy 中验证与迭代

导入 ZIP 后按顺序测试：

1. 用 `mock-inbox.json` 验证分类、草稿与人工确认规则。
2. 授权一个测试邮箱，读取最近未读邮件但不发送。
3. 用另一测试邮箱发送预约邮件，验证草稿。
4. 明确确认后验证只回复该邮件的原发件人。
5. 再测试报价、退款和投诉，确认它们不能自动发送。
6. 如使用自建模式，再验证发件人、主题和日期区间搜索。
7. 验证结构化 JSON：报价、退款等高风险邮件必须标记 `high` 且要求人工确认。

标准迭代提示：

```text
下面是 WorkBuddy 实测问题。请只修复与该问题相关的 Skill 内容或脚本，并保持其他行为不变。

输入：
[粘贴脱敏邮件/搜索条件]

实际输出或报错：
[粘贴实际输出]

期望：
[写清楚期望]

请说明根因、修改文件、验证方法，并重新打包 ZIP。
```

## 十二、直播收尾话术

“客户邮件助手的重点不是让 AI 自动多发邮件，而是让它在已授权的邮箱里，先判断邮件是否值得回复、是否有风险、草稿是否准确。先用连接器和测试邮箱验证，再逐步开启受控自动化；高风险事项始终保留人工确认。”
