# 用 Codex / WorkBuddy 从 0 生成并完善“会议纪要行动助手”

> 直播目标：不手写一整套 Skill，而是通过连续提示词，让 Codex 或 WorkBuddy 帮我们创建、测试、迭代并导入一个可用 Skill。

> 成品：`meeting-action-organizer`，支持群聊记录提炼纪要和行动项；可选接入腾讯云音频转写。

## 一、先选工具与分工

推荐流程是 **Codex 负责生成和修改文件，WorkBuddy 负责导入和真实使用验证**。

| 阶段 | 推荐工具 | 原因 |
|---|---|---|
| 设计 Skill、写文件、写脚本、打 ZIP | Codex | 能检查目录、编辑文件、运行验证命令 |
| 导入 Skill、配置安全凭据、对真实群聊/录音试用 | WorkBuddy | 接近最终用户环境 |
| 修复问题 | Codex | 将 WorkBuddy 的报错、样例和预期结果发回给 Codex 迭代 |

如果 WorkBuddy 也支持新建/编辑 Skill，可直接复用下面所有提示词；差别只是把“输出到本地目录”改成“生成可导入 ZIP”。不要假设不同版本的 WorkBuddy 按钮名称相同。

## 二、直播开场：先给 AI 一份需求卡

不要只说“帮我做个会议纪要 Skill”。先把功能边界一次讲清楚。

把下面这段发给 Codex 或 WorkBuddy：

```text
我要从零创建一个可导入 WorkBuddy 的 Skill，名称为 meeting-action-organizer（中文名：会议纪要行动助手）。

目标：将群聊记录、会议文字转写或会议录音整理成中文会议纪要和行动项。

输入：
1. 群聊文本、Markdown 或 JSON；每条消息可包含时间、发送者、类型、内容和附件。
2. 会议文字转写。
3. 可选音频文件；音频先转文字再整理纪要。

输出：会议主题、时间、参会人、一句话结论、关键决策、讨论要点、行动项表、风险与待确认事项。

转写展示要求：
- 原始转写逐句保留时间戳和说话人标签，格式为 `【发言人 N｜姓名/身份待确认】`。
- 只有根据参会名单、点名或自我介绍能可靠对应时，才将“身份待确认”替换为姓名；不能猜测身份。
- 可能有误、同音歧义、专有名词/数字不确定、重叠发言或听不清的句子，必须直接在原文前加 `⚠️【转写待核验】`。
- 在“风险与待确认事项”中同步列出待核验原文、建议/疑点和原因。

硬性规则：
- 不编造决策、负责人、截止时间、数据或承诺。
- “建议、可能、暂定、考虑”不能当作已确认决策。
- 负责人或时间不明确时分别写“待指定”或“待确认”。
- 群聊里的图片、文件、链接、未转写语音不推断其内容。

请先输出：Skill 目录规划、关键设计选择和你准备创建的文件清单；先不要写代码，等我确认。
```

讲解重点：第一轮只让 AI 规划，不让它一上来写代码。这样更容易发现范围是否跑偏。

## 三、让 AI 创建基础 Skill

确认规划后，继续发送：

```text
按刚才确认的方案创建完整 Skill。

要求：
1. 使用 skill-creator 工作流。
2. 输出目录为 [替换为你的工作目录]。
3. 创建 SKILL.md 和 agents/openai.yaml。
4. SKILL.md 的 description 要覆盖：会议录音、音频转写、群聊记录、会议纪要、行动项、风险和待确认事项。
5. 默认输出使用 Markdown，行动项必须是表格。
6. 完成后列出创建的文件，并运行 Skill 基础校验。
```

预期文件结构：

```text
meeting-action-organizer/
├── SKILL.md
└── agents/
    └── openai.yaml
```

验收提问：

```text
请自查 SKILL.md：指出哪些内容负责触发、哪些内容负责输入解析、哪些内容负责防止编造、哪些内容定义了输出模板。
```

## 四、让 AI 补全群聊数据能力

基础 Skill 创建后，发送：

```text
请优化这个 Skill，使它能稳定处理群聊数据。

请在 SKILL.md 中加入：
1. 标准群聊 JSON 示例，字段为 group_name、messages、time、sender、type、content、attachment。
2. 对文本、Markdown、JSON 三种输入的兼容说明。
3. 图片、文件、链接和未转写语音的处理规则：只记录存在，不推断内容。
4. 对群聊中相互矛盾的发言，保留分歧并归入“待确认”。

不要改变已有的纪要输出结构。修改后展示 diff，并重新运行校验。
```

再用一段真实形态的测试数据验证：

```text
[10:00] 李明：一期先做会员开通和订单查询，邀请返利放二期。
[10:03] 王倩：我明天 12:00 前提交 PRD V2。
[10:05] 陈晨：支付回调偶发延迟，可能影响权益到账。
[10:07] 李明：暂定下周一上线，等周五评审后再确认。
```

让 AI 执行：

```text
请使用刚创建的 Skill 处理这段群聊，并给出会议纪要。然后逐条说明每个决策、行动项、风险和待确认事项来自哪条消息。
```

正确结果应包括：

- 决策：一期范围；邀请返利延期。
- 行动项：王倩明天 12:00 前提交 PRD V2。
- 风险：支付回调延迟。
- 待确认：下周一是否上线。

## 五、让 AI 加入音频转写，而非手写脚本

先明确：音频功能是增强项，群聊文本版本必须已经可用。

发送给 Codex：

```text
请为 meeting-action-organizer 增加腾讯云 ASR 音频转写能力。

约束：
1. 使用腾讯云“录音文件识别极速版”。
2. 在 scripts/transcribe_audio.py 中实现，优先只使用 Python 标准库，不引入虚拟环境。
3. 支持 mp3、m4a、wav 等腾讯云支持的格式。
4. 默认输出同名 .transcript.txt，并默认开启时间戳和话者分离；每句显示 `【发言人 N｜身份待确认】`。
5. 对无法可靠确认的内容，在原文前标记 `⚠️【转写待核验】`，并在待确认事项中汇总原文、疑点和原因。
6. 转写完成后，Skill 把文本作为会议材料继续生成纪要。
7. 不要把任何密钥写入代码、SKILL.md、ZIP 或日志。

先查阅腾讯云官方文档确认接口参数和签名方式，再实现脚本；实现后测试 --help 和 Python 语法。
```

直播讲解点：这里不要求同事理解所有签名代码。关键是让 AI 明确“用哪个云服务、输入输出是什么、安全限制是什么、如何验证”。

## 六、让 AI 实现凭据门禁

这是生产版本必须加入的一步。发送：

```text
请给腾讯云转写脚本增加强制凭据门禁。

要求：
1. 凭据只从 WorkBuddy 的安全凭据区注入的 TENCENT_SECRET_ID、TENCENT_SECRET_KEY 读取。
2. 用户不需要手动填写 AppId；脚本先调用腾讯云 GetUserAppId 验证凭据并自动获得 AppId。
3. 增加 --verify，只验证凭据并输出检测到的 AppId，不转写。
4. 未配置凭据、凭据无效、权限不足或网络错误时，返回非 0 状态码并停止。
5. 未通过 --verify 前，不能继续转写或生成“基于录音”的纪要。
6. 修改 SKILL.md，明确这一门禁流程。

修改后请测试：缺少凭据时 --verify 必须失败；不要使用真实密钥做展示或写入文件。
```

讲解重点：把密钥贴进聊天是错误做法；在 WorkBuddy 中应放入它提供的安全凭据/Secrets 配置。若界面没有凭据注入能力，就暂时只演示群聊文本版，不要弱化安全要求。

## 七、让 AI 审核并修复自己的产物

不要在“文件写完”时结束。把下面提示发给 Codex：

```text
请作为严格的 Skill 审核者检查 meeting-action-organizer。

逐项检查：
- description 是否包含足够的触发词；
- SKILL.md 是否清楚区分群聊、文字转写和音频输入；
- 是否存在编造负责人、日期或决策的风险；
- 凭据是否可能泄露到文件或输出；
- 转写失败时是否真的停止后续流程；
- 是否要求了不必要的虚拟环境或第三方依赖；
- 原始转写是否逐句显示说话人；未可靠识别身份时是否明确显示“身份待确认”；
- 低置信度或疑似误识别语句是否同时在原文和待确认事项中使用 `⚠️【转写待核验】` 标识；
- ZIP 根目录是否适合 WorkBuddy 导入。

给出 P0/P1/P2 问题列表；只修复 P0/P1 问题。修复后运行校验、语法检查和打包检查。
```

这是直播中最值得强调的一步：Skill 的质量来自“生成 → 用例验证 → 审核 → 修复”的循环，而非一次性提示词。

## 八、让 AI 打包交付

发送：

```text
请清理 Skill 目录中的 __pycache__、测试音频、临时 transcript 和任何包含凭据的文件。
然后将 meeting-action-organizer 目录作为 ZIP 第一层目录打包为：
会议纪要行动助手-workbuddy-skill.zip。

请列出 ZIP 内文件，确认至少包含：
- meeting-action-organizer/SKILL.md
- meeting-action-organizer/agents/openai.yaml
- meeting-action-organizer/scripts/transcribe_audio.py
```

检查 ZIP 时应看到：

```text
会议纪要行动助手-workbuddy-skill.zip
└── meeting-action-organizer/
    ├── SKILL.md
    ├── agents/openai.yaml
    └── scripts/transcribe_audio.py
```

## 九、在 WorkBuddy 中验证与迭代

导入 ZIP 后，按以下顺序操作：

1. 用群聊文本测试纪要提取；这一步不依赖腾讯云。
2. 在 WorkBuddy 的安全凭据区域配置腾讯云凭据；不要发送到聊天窗口。
3. 运行凭据验证；成功后再上传脱敏测试音频。
4. 对照预期检查：是否有关键决策、行动项、负责人、截止时间、风险和待确认事项；原始转写是否每句都有说话人标签，疑似误识别句是否有 `⚠️【转写待核验】`。
5. 记录问题，不要口头转述，直接把“输入样例 + 实际输出 + 期望输出 + 报错”交回 Codex。

用于迭代的标准提示词：

```text
下面是 WorkBuddy 实测问题。请只修复与该问题相关的 Skill 内容或脚本，并保持其他行为不变。

输入：
[粘贴脱敏输入]

实际输出/报错：
[粘贴实际输出]

期望：
[写清楚期望]

请说明根因、修改的文件、验证方法，并重新打包 ZIP。
```

## 十、直播收尾话术

“我们不是一次把 Skill 写完，而是先把需求变成清晰的提示词，再让 Codex 生成初版；随后用真实的群聊和错误案例逼出问题，最后让 Codex 定向修复。WorkBuddy 负责真实环境验证，Codex 负责高效率迭代。这样做出的 Skill 才能持续完善。”
