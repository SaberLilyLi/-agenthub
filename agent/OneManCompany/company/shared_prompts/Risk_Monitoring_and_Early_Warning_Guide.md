# 项目风险监控与预警操作指南（适用于 EA 和管理层）

## 1. 目标与适用范围

本指南帮助 EA（执行助理）及 COO、CSO 等管理人员在项目跟进与验收过程中快速、准确地审查错误日志，识别工程师的系统性错误和技术阻塞，并建立有效的预警与解阻机制，防止项目因技术问题陷入死循环或停滞。

适用范围：所有包含代码产出的软件开发、迭代交付和项目验收流程。

## 2. 核心审查步骤与操作流程

### 2.1 验收前基础审查（预防）

工程师提交交付物，例如提交验收申请或把项目状态更新为 `completed` 时，管理层必须进行首轮审查。

- **核验交付物清单与路径**
  - **动作**：检查真实交付文件是否保存在项目指定的 `workspace` 目录。
  - **预警信号**：文件保存在旧目录、临时目录（如 `/tmp`）或默认根目录。
  - **应对方式**：立即拒绝，并明确指出正确存放路径。
- **审查输出信息完整性**
  - **动作**：检查任务输出 `output` 和详细日志 `detail` 是否被截断，例如以异常字符或不完整句子结尾。
  - **预警信号**：文本截断可能表示系统触发长度限制（Token 超限），或生成日志时发生内部错误。
  - **应对方式**：要求提交者或工程师补充完整信息，并检查是否触发 Token 限制，例如 `Error code: 402`。

### 2.2 深入审查错误日志（识别系统性问题）

项目被拒绝或工程师报告遇到问题时，必须彻底审查日志。

- **动作**：查看项目时间线 `timeline` 或任务执行日志，重点搜索 `Error`、`Exception`、`Failed` 等错误标识。
- **常见系统性错误与预警信号：**
  - **递归失败或死循环**
    - **信号**：同一任务或子任务被反复分派，例如同一“文件路径错误”整改任务多次分派；工程师回复完全相同，或陷入“修复失败—再次修复—再次失败”的循环。
    - **示例**：在 `iter_002` 项目中，EA 反复以路径错误拒绝，工程师多次声称已迁移文件，但 `status` 等元数据没有更新，最终形成循环。
  - **构建或依赖级联失败**
    - **信号**：日志频繁出现 `ModuleNotFoundError`、`ImportError`、`Build failed`，修复一个问题后立即出现另一个依赖错误。
  - **运行时崩溃**
    - **信号**：日志出现 `Segmentation fault`、`Out of memory`、`Connection refused` 等严重系统级错误。
  - **资源或权限限制**
    - **信号**：`Error code: 402` 表示资金或 Token 不足；`Permission denied` 表示无权访问文件或目录。

### 2.3 技术阻塞识别与解除

- **识别阻塞**：上述预警信号出现超过 **2 次**，或导致项目停滞超过预期时长，例如半天，即判定为“技术阻塞”。
- **解阻机制：**
  1. **暂停自动流程**：立即停止自动任务分派，防止机器循环消耗资源。
  2. **人工介入诊断**：COO 等管理人员必须亲自介入，不得只看工程师的自评或回复；应深入检查 `project.yaml`、`iterations.yaml` 等底层配置和真实文件系统。
  3. **查明根因**：区分“文件确实放错位置”和“系统元数据未更新”，例如 `status: in_progress` 导致持续重试。
  4. **强制干预**：在确认实际工作已完成后，可允许或授权工程师修改系统元数据，或由管理层手动更新状态以打破循环。

## 3. 预警级别与升级路径

| 预警级别 | 触发条件 | 应对动作 | 升级路径 |
|---|---|---|---|
| **低（L1）** | 单次交付路径错误、偶发编译错误、轻微日志截断 | 在任务评论中指出问题，要求工程师整改 | 同一问题重复 2 次时升级为中级 |
| **中（L2）** | 任务陷入死循环（如分派 3 次以上）、频繁依赖错误、Token 限制（如 402 错误） | 暂停自动流程，由管理层人工审查日志并定位阻塞 | 涉及底层系统配置或长时间无法解决时升级为高级 |
| **高（L3）** | 系统性崩溃、严重权限问题、项目因技术阻塞完全停滞 | 立即通知 CEO，召开紧急技术会议；必要时修改底层框架或追加预算 | 登记到重大风险清单并开展事后复盘 |

## 4. 案例复盘：“愤怒的小鸟” `iter_002` 死循环事件

- **症状**：EA 以文件存放路径错误为由反复拒绝项目；工程师多次回复已迁移文件，但任务仍持续被重新分派。
- **审查盲点**：EA 和 COO 只依赖表层路径检查，没有深入核验 `project.yaml` 或 `iterations.yaml` 等项目元数据。
- **根因**：文件实际上已经迁移到正确目录，但驱动验收循环的 YAML 文件中，`status` 仍为 `in_progress`，`output` 为空，系统因此持续判定任务未完成。
- **正确动作**：发现重复分派这一递归失败信号后，管理层应立即介入；先核实文件系统确认文件就位，再检查 YAML 配置，并授权工程师把状态更新为 `status: completed`、补齐 `output`，从而打破循环。

## 5. 归档与执行要求

1. 本指南自发布之日起生效，所有新项目验收都必须按本指南执行基础审查和深度日志审查。
2. EA（Pat）每次验收前必须明确执行“防截断”和“防死循环”检查。
3. COO（Alex）及其他管理人员对 L2 及以上预警承担主要介入责任。
4. 本培训记录和指南应归档至公司共享知识库或项目管理规范目录，作为后续考核依据。
